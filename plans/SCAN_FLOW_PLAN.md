## 0. 문제와 목표

실측: 7페이지 본문(태그 제외, 공백 제외) **4,926 ~ 9,232자**. 500자/분 기준 **10~18분**.
채용 담당자의 실제 행동 모델은 "전부 읽기"가 아니라 **훑기 → 한 곳 정독 → (동기 발동 시) 원본 정독**이다.
지금 페이지는 훑기와 정독의 층이 갈라져 있지 않아, 훑는 사람도 전체 분량을 마주한다.

**목표 수치 (판정 기준):**

| 층 | 내용 | 예산 |
|---|---|---|
| L0 진입 | 첫 화면 블록만으로 문서 전체 파악 | **≤ 60초 (≤ 250자 + 전시물)** |
| L1 스캔 | 모든 섹션의 제목 + 한 줄 결론 통독 + **상세 1개 섹션** 정독 | **합산 ≤ 120초 (스캔 경로 ≤ 1,100자)** |
| L2 원본 | 요약본·원본 슬라이드 갤러리, 접힌 상세 | **예산 제외 (무한)** |

**스캔 경로 공식** (검증 스크립트가 이 식으로 잰다):
`L0 글자수 + Σ(각 섹션 h2 + sec-key) + max(섹션별 노출 상세 글자수) ≤ 1,100자`

이미지·표·카드 그리드 같은 **전시물은 예산에 넣지 않는다**(눈이 훑는 속도가 텍스트와 다르다).
단 전시물도 무한정은 아니다 — §3-C의 개수 상한을 따른다.

**뷰포트 가중 PC 9 : 모바일 1 (사용자 지시).** 이 설계의 모든 판정 기준은 **1280~1920px에서 잰다.**
- 모바일은 **깨지지 않는 것만 보장**한다(가로 스크롤 0 · 1열 폴백 · 콘텐츠 유실 0). 첫 화면 노출 같은 최적화 목표는 모바일에 적용하지 않는다.
- R3.5에서 남은 375px 미달 2건(onepluone·hesti)은 **이 가중치에 따라 수용 가능한 결함으로 강등**한다. 히어로 요소를 지우면서까지 모바일을 맞추지 않는다.
- 반대로 **PC에서 놀고 있는 가로 공간은 이 설계의 최대 자원**이다 — §1-C.

## 1. 3층 구조 정의

### L0 — 진입 블록 (첫 화면, ≤ 60초)

R3.5가 만든 것을 그대로 층의 부품으로 인정한다. 구성(위에서부터):

1. **신원 스트립**(R2, 스티키) — 배현 · 게임기획 신입 · 메일 · 허브. *페이지별 직군 표기 없음(R3.5에서 삭제됨 — 재도입 금지, ENTRY_FLIP §1 입구 선택제의 급소).*
2. **원작 게임 헤더**(R3.5, 원작 있는 4편) — 「호라이즌 제로 던」 식 게임명 + 문서 종류 + 원작 대표 이미지. 인사담당자가 "아 이 게임의 역기획서구나"를 첫 화면에서 캐치.
3. **문서 한 줄 + 핵심 수치 2~3개**(R3.5 리드의 잔존 부품).
4. **목차** — 기존 목차 nav를 L0의 "전체 지도"로 인정. 섹션 제목이 곧 목차 항목이므로 별도 요약 블록을 신설하지 않는다.

L0에서 **하지 않는 것**: 읽기 시간 표기(삭제됨 — 재도입 금지), 직군 표기, 슬라이드 분량 자랑.

5. **★ 대표 슬라이드 스트립**(신설, §1-B) — 직접 만든 문서 4~6장을 첫 화면에서 보여 준다. **증거 우선 원칙.**

### L1 — 스캔 본문 (섹션들)

모든 콘텐츠 섹션이 동일한 3부품 리듬을 갖는다:

```
<h2>제목</h2>
<p class="sec-key">한 줄 결론</p>        ← 신설 부품. 훑을 때 읽히는 유일한 텍스트
(전시물 ≤ 2개 + 노출 산문 ≤ 400자)      ← 멈춘 사람이 읽는 상세
(<details class="fold"> 초과분 </details>) ← 선택적. L2로 강등된 심화
```

### L2 — 원본 (예산 제외)

- 요약본/원본 슬라이드 갤러리 섹션: **무변경**. 이 층이 전량을 보존하므로 L1의 산문을 자를 수 있다.
- `<details class="fold">`: L1에서 강등된 HTML 전용 심화(슬라이드에 없는 표·해설). 네이티브 요소라 no-JS에서도 동작.

## 1-B. 요약본·원본을 어디에 둘 것인가 — 판단

### 전제: 무엇이 상품이고 무엇이 포장지인가

채용 담당자가 사려는 것은 **배현이 직접 만든 기획 문서**다. HTML 페이지는 그 문서를 어떻게 읽어야 하는지 알려주는 **안내문**이다.
그런데 현재 구조는 안내문을 끝까지 읽어야 상품에 닿는다(원본 갤러리가 전부 맨 마지막 섹션).
게다가 채용 담당자가 실무에서 매일 보는 기획서 형태는 **슬라이드**다 — 슬라이드를 먼저 보여 주는 것은 "실무 산출물을 낼 줄 아는 사람"이라는 신호이기도 하다.

**반대 위험도 실재한다.** 슬라이드를 전면에 크게 깔면 "PPT를 이미지로 올린 사이트"로 읽혀, HTML이 더한 가치(라벨 규율·정직한 경계·데이터 재구성)가 통째로 안 읽힌다.

→ 그래서 **한 덩어리로 두지 않고 셋으로 쪼개 각각 다른 층에 배치한다.**

### 결론 — 슬라이드 3단 배치

| 무엇 | 어디 | 왜 |
|---|---|---|
| **대표 4~6장**(신설) | **L0 첫 화면** | 30초 안에 "진짜 만들었다"를 증명. 스크롤 없이 보이는 유일한 증거 |
| **요약본 전량**(16p·18p) | **본문 앞부분**(현행 유지) | 훑는 사람의 최적 매체. 슬라이드는 한 장=한 메시지라 산문보다 빠르다 |
| **원본 전량**(24~36p) | **맨 아래**(현행 유지) | 동기가 발동한 사람만 필요. 위로 올리면 스크롤을 잡아먹어 해설이 죽는다 |

**hzd·endfield는 이미 요약본이 3~4번째 섹션에 있다 — 이 배치가 옳았다. 바꾸지 않는다.**
요약본이 따로 없는 5편(onepluone·foxforest·unreal·hesti·nidalee)은 **요약본을 새로 만들지 않는다**(사실 창작 금지). 대신 원본에서 대표 4~6장을 골라 L0 스트립만 세운다.

### 대표 슬라이드 스트립 사양

- 위치: L0 하단, 목차 위. PC에서는 **가로 1열 4~6장**(§1-C의 2단 배치 시 우측 칼럼).
- 고르는 기준: **그 문서의 주장을 혼자 증명하는 장**(구조도·데이터 표·비교 도식 우선, 표지·목차·인사말 제외).
- 클릭 시 기존 라이트박스로 확대(이미 구현돼 있음). "전체 N장 보기 ↓"로 해당 갤러리 앵커 이동.
- above-fold라 **이 스트립 이미지만 `loading="eager"`**, 나머지 갤러리는 lazy 유지.
- 캡션은 페이지 번호가 아니라 **그 장이 보여 주는 것**(예: "P.04 — 서사 12단계와 진입 분기"). 지금 갤러리 캡션은 "핵심 요약본 P.04"뿐이라 정보가 0이다.

## 1-C. 어필 최적화 구조 — PC 9의 활용

### 채용 담당자의 실제 판단 4단계

| 단계 | 묻는 것 | 지금 페이지의 답 | 처방 |
|---|---|---|---|
| ① 판별 30초 | 뭘 한 사람인가 | R3.5로 해결됨(원작 배지·한 줄·수치) | 유지 |
| ② **검증 1분** | **진짜 본인이 한 게 맞나** | **증거가 맨 뒤에 있어 답이 없다** | **L0 슬라이드 스트립(§1-B) + 킬러 카드 승격** |
| ③ 적합 1분 | 우리 일에 쓸 수 있나 | 섹션을 다 읽어야 알 수 있다 | sec-key 통독(§2) |
| ④ 심화 ∞ | 얼마나 깊나 | 원본 갤러리 — 잘 돼 있다 | 유지 |

**②가 이 포트폴리오의 최대 구멍이다.** 신입 지원자에게 채용 담당자가 가장 크게 걸리는 의심은 "이거 진짜 혼자 했나"인데, 그 답이 되는 자산이 전부 문서 맨 뒤에 있다.

### 킬러 카드 승격 (페이지별 1개, L0로)

지금 각 페이지의 최강 카드는 예외 없이 **문서 후반부**에 있다. 훑는 사람은 도달하지 못한다.

| 페이지 | 킬러 카드 | 현재 위치 | 처방 |
|---|---|---|---|
| onepluone | 「역할 경계 — 정직 버전」 3열 표 | 8/9번째 섹션 | L0에 **한 줄 훅** + 앵커("내가 한 것과 아닌 것을 갈라 적었습니다 ↓") |
| hesti | 카뮤 대조(제안 후 원작에 유사 컨셉 출시) | 맨 뒤 | L0 수치 자리 하나를 이 훅으로 |
| hzd·endfield | 「사실·해석·제안의 경계」 라벨 규율 | 7번째 | L0에 신뢰 배지 한 줄 |
| unreal | 1.8m 실측 · #limits(못 하는 것) | 중·후반 | L0 수치에 "실측 1.8m 기준" 노출 |
| foxforest | 전시 134명 체험 · 피드백 9명 반영 | 리드에 이미 있음 | 유지 |
| nidalee | 3엔딩 비선형 퀘스트 구조 | 후반 | sec-key로 세움 |

**승격은 복제가 아니라 훅이다** — 본문은 그대로 두고, L0에 **한 줄 + 앵커 링크**만 놓는다. 같은 내용을 두 번 쓰면 분량이 다시 늘어난다.

### PC 가로 공간 활용 (9의 실체)

현재 `--maxw:1120px` 단일 칼럼. **1920px 모니터에서 800px이 놀고 있다.** 세로로만 흐르니 스크롤이 길어지고, 스크롤 길이가 곧 "2분"을 깨는 주범이다.

- **L0 2단 배치**: 좌(제목·한 줄·수치·킬러 훅) ‖ 우(대표 슬라이드 스트립). 첫 화면에서 **말과 증거가 동시에** 보인다.
- **L1 2단 배치(선택, §5-S4)**: 좌(h2·sec-key·상세 400자) ‖ 우(그 섹션의 전시물, `position:sticky`). 해설을 읽는 동안 그림이 따라온다 → **세로 길이 최대 40% 감소.**
- 적용 폭: **≥1200px에서만** 2단, 그 아래는 지금처럼 1열(모바일 폴백은 자동으로 안전).
- ⚠ `--maxw`를 키우는 것과는 다르다. **판독 폭(한 줄 글자수)은 건드리지 않는다** — 본문 칼럼은 지금 폭을 유지하고 남는 공간에 전시물을 옮기는 것이다. 원쁠원만 `--maxw:880px`이라 2단 시 칼럼 배분을 따로 잡아야 한다.

## 2. `.sec-key` — 한 줄 결론 부품 사양

### 마크업·CSS

- `assets/style.css`에 **1회 정의**(CLAUDE.md §2-5 — 색 하드코딩 금지, `var(--accent)`·`var(--ink)` 상속).
- h2 바로 아래 고정 위치. 시각 사양: 본문(15.5px)과 확실히 구분되는 **17.5~19px · 볼드 · accent 좌측 마커**(3px 바 또는 ▍). 훑는 속도에서 h2 다음으로 눈이 걸리는 유일한 요소여야 한다.
- `details.fold`: summary에 `+ 자세히` 류의 절제된 라벨, 열림 상태 스타일 포함. 인쇄 시 접힌 내용은 요약만 나가는 것을 **의도된 트레이드오프로 수용**(원본 갤러리가 인쇄를 담당).

### 집필 규칙 (구현 에이전트가 지킬 것)

1. **≤ 45자.** 두 문장 금지.
2. **주제가 아니라 결론.** "밸런싱 구조를 설명한다"(주제) ✗ → "코드를 열지 않고 시트 3장으로 밸런스를 돌렸다"(결론) ✓.
3. **기존 문장의 증류만.** 각 섹션의 현재 `p.lede`·본문에서 뽑는다. 페이지에 없는 사실·수치 발명 금지.
4. 이 사이트의 라벨 규율 준수 — 관측/추론/제안이 갈리는 문장이면 해당 라벨의 표현을 따른다.
5. 갤러리 섹션(요약본/원본 전문)과 목차에는 sec-key를 달지 않는다.

### 예시 (가마솥, 실제 본문에서 증류 — 구현 시 원문 대조 후 확정)

| 섹션 | sec-key 초안 |
|---|---|
| 이야기가 목표·동선·전투·보상으로 이어지는 구조 | 한 줄의 이야기가 4개의 축으로 나뉘어 데이터까지 내려가는 경로를 확인했다 |
| 데이터로 정리한 퀘스트 | 화면 관찰만으로 퀘스트 5단계 체인을 기획서 표 형식으로 복원했다 |
| 개선 제안 | 진입 경로가 둘로 갈릴 때 대사가 어긋난다 — 조건 분기 1건을 제안했다 |

## 3. 상세(노출 본문) 감량 규칙

### A. 산문 상한 — 섹션당 노출 ≤ 400자

초과분의 처리 우선순위:
1. **삭제** — 원본 슬라이드가 같은 내용을 담고 있으면 지운다(L2가 보존을 담당). 대상: 슬라이드 내용의 산문 재서술, 같은 말의 반복, 배경 설명.
2. **접기(`details.fold`)** — 슬라이드에 없는 HTML 전용 가치(직접 만든 표의 행 다수, 긴 해설)만.
3. **유지** — 400자 안에서 가장 강한 문장만 남긴다.

### B. 절대 지키는 것

- **사실 발명 금지. 수치 변경 금지.**
- **킬러 콘텐츠는 자르지 않는다** (전량 노출 유지): 원쁠원 「역할 경계 — 정직 버전」 표, 헤스티 카뮤 대조 기록, 각 페이지 「사실·해석·제안의 경계」 절(짧게는 다듬되 접지 않는다 — 정체성 부품), unreal-level `#limits`(못 하는 것).
- **AI 재구성 고지**(R3에서 이동한 전문)는 위치·내용 유지.
- 갤러리 섹션 무변경. `<span class="site-bar__where">` 형식·`<nav class="proj-nav">` 불가침(관리자 publish 영역).

### C. 전시물 상한 — 섹션당 노출 ≤ 2개

- 표·카드 그리드·figure 중 **그 섹션의 주장을 증명하는 최강 1~2개**만 남긴다.
- 요약본 슬라이드 재게재 figure(`ifig`)가 섹션에 2장 이상이면 1장으로 — 어차피 갤러리에 전량 있다.
- 남길 우선순위: 직접 만든 표/다이어그램 > 게임 스크린샷 > 슬라이드 재게재.

### D. CLAUDE.md §4 개정 (구현 마지막 라운드에서)

"프로젝트 페이지 본문은 의미 변경 금지"는 **이 설계로 대체된다**. 개정문:
"프로젝트 페이지는 3층 스캔 구조(SCAN_FLOW_PLAN)를 따른다. 본문 감량·재배치는 허용하되 **사실·수치의 발명과 변경은 금지**, 원본 갤러리는 전량 보존."

## 5. 구현 라운드 (Opus 위임 단위)

> 공통: 병렬 에이전트 금지 아님 — **S2·S3는 파일이 겹치지 않아 병렬 가능**하나, style.css는 S1에서만 만진다(이후 라운드는 HTML만). 커밋은 라운드마다. publish 검증은 사본 대상.

- **S0 — 증거 우선 (§1-B·§1-C, 7편 공통)**: ① 대표 슬라이드 스트립 부품 CSS + 7편 장 선정·주입(캡션 재작성 포함) ② 킬러 카드 훅 1줄씩 L0에 ③ L0 2단 배치(≥1200px). **S1보다 먼저 한다** — 감량(자르기)보다 증거 배치(더하기)가 어필 효과가 크고, 되돌리기도 싸다.
- **S1 — 부품 + 시범 + 계측기**: ① `.sec-key`·`details.fold` CSS(style.css 1회) ② 스캔 경로 계측 스크립트(§0 공식 구현, scratchpad — 이후 라운드가 재사용) ③ **hzd-quest 전면 적용** ④ 검증 후 **사용자 검수 게이트** — sec-key 문장 전부와 감량 판단을 보고, 승인 후 S2 진행.
- **S2 — 무거운 3편**: endfield · hesti · nidalee (S1 승인된 문법 복제).
- **S3 — 가벼운 3편 + 마감**: onepluone · foxforest · unreal-level + CLAUDE.md §4 개정 + ENTRY_FLIP_PLAN 상호참조 갱신.
- **S4 — (선택) L1 2단 배치**: §1-C. 세로 길이 최대 40% 감소. S1~S3로 목표 수치를 이미 달성했으면 생략 가능 — **비용이 가장 크고 회귀 위험도 가장 크다**(7편 히어로 문법 5종 위에 얹힌다).

**라운드별 검증**: ① 스캔 경로 ≤ 1,100자(계측 스크립트) ② 노출 본문 목표치(§4 표) ③ publish 바이트 동일 ④ **1280·1920px 판정 / 375·760px는 안 깨지는지만**(§0 가중치) ⑤ fold 동작(no-JS 포함) ⑥ 킬러 콘텐츠 전량 노출 잔존 grep ⑦ S0은 above-fold 이미지 로딩 무게(eager 4~6장 합계) 확인.

## 6. 위험

1. **한 줄 결론의 품질이 이 설계의 전부다.** 45자가 약하면 "훑고 그냥 지나가는" 문서가 된다. → S1 검수 게이트가 방어선. 사용자가 hzd의 sec-key를 승인한 뒤에만 확산.
2. **감량은 되돌리기 비싸다.** 삭제된 산문은 git 이력에만 남는다. → 라운드별 커밋 + 커밋 메시지에 섹션별 감량 요지 기록.
3. **접힌 내용은 Ctrl+F·인쇄에서 약하다.** → fold는 최후수단(§3-A 우선순위), 킬러 콘텐츠 접기 금지.
4. **문서 개성 훼손.** 히어로 문법 5종·페이지 고유 색·전시물은 유지 — 자르는 것은 산문이지 정체성이 아니다.
5. R4(하단 도크)·R6(허브 정리)와 독립 — 순서 무관. 단 R3.5가 리드를 바꾸는 중이므로 **S1은 R3.5 완료·커밋 후 착수**.

## 7. 사용자 결정 필요

1. **시범 페이지 = 가마솥(hzd) 승인 게이트** — S1 결과를 보고 문법을 확정한 뒤 6편에 확산. (기본값: 이대로)
2. **접기(details) 허용 범위** — 기본값: 슬라이드에 없는 HTML 전용 심화만 접고 나머지는 삭제(원본 갤러리 의존). 접기 자체가 싫으면 전부 삭제로 통일 가능.
3. **~~헤스티 카뮤 대조를 L0 훅으로 승격할지~~ → §1-C에서 승격으로 확정**(킬러 카드 표에 편입).
4. **S4(L1 2단 배치)를 할 것인가** — PC 9 가중치를 가장 크게 활용하는 수단이지만 비용·회귀 위험이 가장 크다. 기본값: **S1~S3 결과를 보고 결정**(목표 수치를 이미 달성했으면 생략).
5. **헤스티 원작 이미지 없음**(R3.5 이월) — 엔드필드 인게임 스크린샷을 주시면 배지에 넣는다. 저장소의 엔드필드 컷은 '무릉 천정원'이라는 다른 장소라 부적합.
